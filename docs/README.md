## 元の着想

> deno-henjiの完全移植ではなく、構想・機能を引き継いだ後継harnessと捉えてほしい。
> 無理やりdenoの機能を移植するのではなく、goの特性を活かした実装を目指す。
> 当然その過程で妥協しなければならない部分も出ると思う。

利用者は現行Henjiの設計思想、特に履歴保存の価値を引き継ぎ、ツールとAgent Workerを発展させたい。
既存コードの再利用には拘らない。Go本体＋QuickJSを仮採用し、下記５点を上位計画へ載せてスパイクで確認する。
このREADMEは当時、後継構想の上位計画として作成した。現在の採用方針は上記の設計文書に従う。議論の経緯は
[2026-10-10の議論メモ](2026-10-10-go-quickjs-discussion-summary.md)を参照する。

## 問題と背景

Denoの開発体制変更を契機に、Henjiを継続して育てる実行基盤を検討した。
利用者には「便利なツールを与えるほどAgentは賢くなる」という開発上の実感があり、
本体の再ビルドを伴わない拡張と、実行中にコードで処理を組み立てる能力を重視する。
履歴保存は、実行を振り返り、設定やツールを改善し、保存した会話を再開するための基盤である。

## 期待する成果

- **永続的な拡張**：tool・hookのソース編集を、本体の再ビルドなしで次のWorkerから使える。
- **その場での拡張**：Agentが生成したJSから登録ツールを組み合わせ、実行結果を次の判断に使える。
- **履歴の継承**：成功した会話だけでなく、失敗・中断・途中のツール実行と使用した構成を振り返り、保存Sessionを再開できる。
- **環境に依存しにくい基礎機能**：基本HTTPはcurlのインストール状況に依存せず、拡張からライブラリやOSコマンドも利用できる。

## 利用者・関係者・利用場面

本人が自分の環境でAgentを使い、外部ツールやhookを整備し、履歴を根拠にWorkerの振舞いを改善する。
生成JSは、複数ツールの結果の加工・集約や、その結果に応じた追加のツール呼出しに使う。
実装・配布を確認する対象OSと環境は、スパイク計画時に本人の実際の利用先から定める。

## 現行手段と不足・選択肢

| 手段 | 満たせること・利点 | 不足・負担 | 現在の扱い |
| --- | --- | --- | --- |
| 現行Deno版を継続 | 履歴と既存の外部TS・生成TSを利用できる | 実行基盤の今後を踏まえた継続判断が必要 | 参照実装として活かす |
| Bun等の外部JSランタイムへ変更 | JS/TSと既存ライブラリの利用を維持しやすい | ランタイム依存と現行実装への適合確認が必要 | 比較済みの未採用案 |

| Go＋QuickJS | JSによるツール合成とGoによる実行・履歴管理を組み合わせられる見通し | API接続、非同期処理、依存の利用・配布を整備する必要がある | 仮採用。スパイクで確認する |

## 事実・仮定・未決事項

### 確認済みの事実

- 現行Henjiは外部toolのモジュールをWorker起動時に読み込み、`run_typescript`で生成コードを実行する。
- 現行履歴は、実行の証拠保存と、正常完了したturnの会話への採用を分けている。失敗・中断や子実行も保存対象である。
- 現行TUIはHTTP APIのクライアントとして動く。後継でもTUIとJSから共通の操作を使う構想と整合する。
- QuickJSのGo組込み候補には非同期Go関数の接続やPromiseの処理を進める機構がある。Henjiに必要な一連の動作は未実証である。

### 採用する方向性

Goを本体の実装言語とし、Goの並行処理と実行管理の特性を活かす。
QuickJSはtool・hookとAgent生成JSの実行基盤として仮採用する。
Go-Henjiの操作とHTTP・ファイル・OSコマンド等の機能を公開APIへ整理し、JSやTUIから利用できる方向で検討する。
共通の操作契約を持つことと、すべての呼出しをHTTP経由にすることは別に判断する。

生成コードはJSでよく、TypeScript実行とWeb標準API互換は必須ではない。
Goのgoroutine、context等に合わせて非同期処理を設計し、DenoのWorkerやイベントループの配置をそのまま再現することは要求しない。

### 未決事項

binding、VMの寿命・共有方法、同一／別プロセス、具体的な公開API・通信形式、依存の取得・配布方式は未決である。
Agent loopまでソース編集可能にするか、全ツールを外部化するか、初期製品の機能範囲は、スパイクの結果も使って判断する。
tool・hookだけの編集可能性でも利用者の要求を満たし得る。旧DBの互換・移行は履歴機構の継承と分けて判断する。

## 中核仮説と検証：スパイクで確認する５点

中核仮説は、Go＋QuickJSで永続的な拡張とその場でのツール合成を成立させ、その過程を履歴へ残せることである。
以下の５点をスパイクの確認対象とする。すべて未実施であり、現時点で合格とは扱わない。

| ID・確認点 | スパイクで観測すること | 成立の判断基準 |
| --- | --- | --- |
| S-01 生成JSから外部ツールを呼ぶ経路 | 生成JS→登録されたJSツール→GoのHTTP・OSコマンド→JSへの結果返却。非同期、例外、キャンセルも観測する | 結果を次の呼出しに使える。失敗が呼出し元へ届き、キャンセル後の実行と後処理の終了を確認できる。VM共有・分離の成立範囲を説明できる |
| S-02 コード内部のツール実行履歴 | 親コード実行と内側のツール呼出しを関連付け、成功・失敗・中断後に保存内容を読む | コードが途中で失敗しても、実行した呼出し・結果・残った副作用を振り返れる。モデルへ返す集約結果と保存する履歴の関係が分かる |
| S-03 ライブラリとGo公開API | 必要なツールの具体例を、Goの基礎機能と実際のJSライブラリで構成する。ソース編集後に次のWorkerで使う | tool・hookの編集が本体再ビルドなしで反映される。利用できる依存、追加のGo APIが必要な場面、取得・配布上の制約を実例から説明できる |
| S-04 履歴保存の価値 | 正常完了の採用、失敗・中断の証拠、使用構成、保存Sessionの閲覧・再開を観測する。履歴増加時の読込み範囲も確認する | 採用済み会話と実行証拠を区別して復元できる。設定を変更して再開しても過去の構成を追跡できる。全履歴を保持しながら、メモリとモデル入力に必要な範囲を取り出せる |
| S-05 配布・起動条件 | 合意した対象OSで、QuickJS・SQLiteを含む本体、外部tool・hookと依存を配布して起動する | 基本HTTPがcurlなしで動く。本体に必要な依存と、追加ツールが要求する外部コマンドを説明できる。配布物でソース編集と次Workerへの反映が成立する |

結果は項目ごとに成立・不成立・未確認を分け、実際の出力・保存記録・起動結果等へ結び付ける。
不成立の場合は、bindingや接続方式の変更で解決する問題か、要求や編集可能範囲の妥協が必要かを整理する。
詳細なAPI、実装順、テストケース、実験コード・ログは対象開発リポジトリで扱う。

## コンセプト上の要求とスパイクMVP

最小の検証経路は、**編集した外部ツールを生成JSから呼び、Goの機能で実処理を行い、結果と失敗を保存履歴で確認する**流れとする。
この経路を土台に、５点に直接対応する最小限の観測を行う。
スパイクの成功は技術的実現性の証拠であり、Agentが日常の作業を完了できる製品としての受入とは分ける。
初期製品のMVPとTUI・非対話run・子Agent等の搭載順は、スパイク後に決める。

## 対象外と判断上の留意点

今回の上位計画では、Deno API・TypeScript・Web標準の完全互換、全機能の詳細設計、旧DBの移行方法を確定しない。
生成コードのために使えるライブラリが狭すぎる、Go側の変更が頻繁に必要になる、実行履歴が欠ける、
停止や配布が実際の利用先で成立しない場合は、目的への影響と代替案を比較して方針を見直す。

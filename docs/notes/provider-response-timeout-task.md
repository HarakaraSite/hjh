## 依頼文

hjhの「モデル応答待ちタイムアウト」を調査し、具体的な対応計画を作成してください。
タイムアウトの条件や時間を決める過程も今回の課題に含みます。まだ実装しないでください。

### 背景

Session `64bbc534`の子`53dcbedc`は、
`openai-chatgpt / gpt-6.1-sol / high`で、
2026-10-15 17:04:05 JSTに4回目のモデル要求を開始しました。
17:15 JSTの確認時点まで新しいthinking・本文・完了・エラーの記録がなく、
親は`collect_agent`で待ち続けていました。
利用者がキャンセルして`/recall`しました。

ただし、保存された記録がないことだけで、SSEの受信自体がなかったとは断定できません。
providerの生成待ちか通信の停滞かも未確定です。

### 目的

応答が返らずエラーにもならない状況から、自動でリトライまたは失敗終了へ進めること。
正常な長い生成・thinkingを不必要に打ち切らないこと。

### 最初に読むもの

- `AGENTS.md`
- [Provider要求の最小リトライ](../plans/provider-single-retry.md)
  特に「モデル応答待ちのタイムアウト」の改善メモ。
- [モデル接続のSDK採用評価](../design/provider-sdk-evaluation.md)
  特にA-2。ただし過去の評価なので現行コードで確認すること。

### 1. 現行経路を確認する

Coreでの親・子実行開始から、認証、HTTP要求、SSE受信、
エラー分類、リトライ、終了保存、TUI表示までを追ってください。
現在の期限・取消・タイムアウトの所有者を明確にしてください。
`53dcbedc`の履歴は読み取り専用で確認して構いません。

### 2. タイムアウト方式を比較し、推奨案を決める

少なくとも以下を区別してください。

- 応答開始まで待つ時間。
- 応答開始後、受信が途絶えてから待つ時間。
- 要求全体の経過時間。

HTTPヘッダ受信、最初のSSEイベント、heartbeat、thinking、
本文、tool call断片のどれを開始・進行と扱うか検討してください。
本文が出ていなくても生成が進む場合を考慮してください。
正常な長時間生成と、今回のような待機をどこまで区別できるか説明してください。

具体的な時間と、固定値か設定可能にするかも推奨してください。
根拠が弱い値は暫定値と明記し、事実・推測・未確認事項を分けてください。
provider差は現行コード・履歴・必要な公式文書から確認し、
未観測の挙動を推測で必須仕様にしないでください。

### 3. 既存処理との接続を決める

- 親・子に共通で適用する。
- タイムアウトした当該要求を確実に終了させてから再送する。
- 既存のprovider timeout分類とリトライ枠を利用する。
- 現行の追加リトライ1回・固定2秒は維持する。
  別メモにある回数増加は今回扱わない。
- 利用者キャンセルやCore停止を自動リトライに変換しない。
- 完了済みtoolや子実行全体を再実行しない。
- 途中の本文・thinkingの保存と、失敗試行の表示を既存契約に合わせる。
- 再送失敗後は既存の失敗終了・`/recall`案内へ返す。

### 4. 計画書を作る

`docs/plans/`に計画書を作成してください。
必要な利用者動作、現行経路、採用案と理由、具体的な時間、
変更範囲、未確認事項、実装スライス、各スライスの確認方法を記載してください。
確認は実際の待機・取消・リトライ経路に対応するものに絞り、
各スライスのfocused testと最後の総合確認を計画してください。

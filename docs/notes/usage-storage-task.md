# solへの依頼：usage詳細の二重保存の整理

2026-10-15、利用者から次の課題の依頼文作成を求められ、改善メモを基に作成。
ツール利用方針・共通helpの実装後の課題候補とする。
今回の範囲は調査・設計・計画まで。計画を利用者が確認する前に実装しない。

## 依頼文

hjhの通常履歴に保存するprovider usageを調査し、二重保存の解消と、
細かな項目別内訳を通常利用の記録から分ける対応計画を作成してください。
まず実際の参照機能を確認し、削減してよい情報と残す情報を決めてください。

### 背景と目的

Session `64bbc534`を2026-10-15 17:46 JSTに読取り専用で集計したところ、
親8実行・子4実行の主要な本文・JSONは約16.75 MiBでした。
usage観測とモデル結果の両方に同じusageが保存され、各113件ありました。

- 片側のusage JSON：約2.48 MiB。
- そのうち項目別トークン内訳`attribution`：片側約2.46 MiB。
- 二重分を合わせた`attribution`：約4.92 MiB、主要データの約29%。

これは特定SessionのJSONを再直列化した集計であり、全provider・全実行での削減率や、
DBファイルの物理縮小量を保証する値ではありません。
二重保存解消と`attribution`の非保存による削減量は重なるため加算しないでください。

利用者は既に「通常利用のための記録と、開発・調査用の精密な記録を分ける」方針を採っています。
今回も通常利用に必要な集計値を維持しながら、保存量と総書込み量を抑えることが目的です。

### 調査・判断する内容

1. provider応答のusageが、ModelResult、Observation、hook、journal、DB、履歴読取り、
   CLI/Core/TUI等へどう流れるか追い、生成・保存・参照の所有者を明確にしてください。
   通常の親・子と、要約専用のモデル呼出しも確認してください。

2. `attribution`を実際に利用している機能や開発用収集経路を確認してください。
   名前が似たhjh独自のcontext attributionとは区別してください。
   参照元がなければ、その事実と探索範囲を報告してください。

3. 通常履歴に残す情報を提案してください。
   入力・出力・合計・キャッシュ・reasoningなどの集計値と、項目別の精密な内訳を区別し、
   現在利用しているproviderの実受信形式・現行参照機能を根拠に判断してください。
   未観測のprovider形式を推測で仕様化しないでください。

4. 同じusageを一箇所へ保存する構成を提案してください。
   既存のrecord ID・親子関係・要求識別子を使えるか確認し、必要性がなければ新しいDB表や
   本文共有の仕組みを追加しないでください。
   モデル応答やライブ観測から情報を消すことと、通常DBへ保存しないことは別に判断してください。
   既存hookや実行時の利用者が必要とする情報を、保存削減のために誤って失わないようにしてください。

5. `attribution`を通常保存から外す場合、調査用の取得を既存の仕組みで行えるか確認してください。
   新しい収集hook・デバッグ基盤の実装は別テーマとし、今回は接続点と未対応範囲を記述するまでにします。

### 計画と確認方法

`docs/plans/`に計画書を作成してください。
利用者が必要とする動作、現行経路、採用案と理由、残す集計値、保存場所、
変える生成・保存・読取り経路、未確認事項、複数の実装スライスを記載してください。

各スライスの実装・focused test・reviewと、最後の総合確認を計画してください。
具体的には、集計値の保存・読戻し、同じ要求のusageが二重保存されないこと、
親子・要約・再試行の要求識別が保たれること、現行の会話再開・履歴表示への影響を、
変更する実経路に対応させてください。TUIのコンテキスト表示はhjh推定のまま維持します。

削減の測定は使い捨てDBで、同じ入力データに対する変更前後を比較してください。
通常保存JSON、論理DB容量、物理ファイル/WAL、可能な範囲の書込み量を区別し、
新しい保存経路の改善と、過去DBの縮小を混同しない計画にしてください。
実プロバイダを呼ばず、既存履歴のusage部分とローカルHTTPで確認できる範囲を明確にしてください。

### 今回の範囲と報告

調査・設計・計画書作成まで。実装は利用者の確認後です。
新しい保存経路を対象とし、既存DBの変換・削除・作り直し・VACUUMは行いません。
過去形式の互換機構を推測で追加せず、必要な切替条件があれば計画で説明してください。
DB非保存mode、コンパクション、tool利用方針、provider timeoutやリトライ回数の変更は対象外です。
実プロバイダ呼出し、実行中runの操作、常用設定の書換え、Core再起動、
コミット・プッシュ・配置は行わないでください。
無関係な変更・未追跡ファイルを変更したり取り消したりしないでください。

最後に、実際にusage詳細を使う機能の有無、推奨する保存内容と場所、
期待できる削減とその限界、スライス、利用者の判断が必要な点だけを簡潔に報告してください。

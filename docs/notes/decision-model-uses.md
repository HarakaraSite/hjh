# hjhでの意思決定モデルの活用候補

記録日: 2026-10-16。利用者との検討メモ。hjhへの導入方式・実装順序は未決。

JevやOpenAI Decisions APIを使い、作業の分岐や候補の選別を、親の生成モデルから
切り出すことを検討する。判断結果を受けたJSが処理を組み立てる構成も候補とする。

## 活用候補

| 用途 | 判断させる内容 |
| --- | --- |
| 子agentへの委譲 | 親で続けるか、子へ任せるか。独立して任せられる範囲はどこか |
| モデルとeffortの選択 | 課題の難しさ・必要能力・価格から、利用可能な候補を選ぶ |
| ツールの選択 | 専用tool、run_jsによる組合せ、外部プログラムのどれを使うか |
| コンパクションの時機 | 今要約するか、原文を維持して進めるか |
| コンパクションの対象 | どの会話範囲を要約し、どの原文・参照を残すか |
| 検索と読取り結果の選別 | URL・ファイル・検索断片の関連度を評価し、詳しく読む対象を選ぶ |
| skillと利用ガイドの読込み | 今必要なskillやツールの詳細説明を選ぶ |
| 子の中間報告への対応 | 親が今扱うか、追加指示を送るか、子の完了まで待つか |
| 行き詰まりの検知 | 同じ検索・失敗の繰返しから、進め方の変更が必要かを判断する |
| 検証内容の選択 | 変更に対応するテスト・実動作確認を選ぶ |
| 過去の会話の読戻し | 現在の質問に関連する過去ターンや記録を候補から選ぶ |

これらは活用案であり、意思決定モデルが実装・テスト・要約生成を直接代替する意味ではない。
例えばコンパクションでは、意思決定モデルが対象ID・範囲を選び、生成モデルが要約し、
JSが参照の付与やコンテキスト差替えを行う構成が考えられる。

## 費用とコンテキストの考え方

「安いモデル」は固定のモデル名だけで指定せず、価格と作業への適性から選べるようにしたい。
価格の比較は通常のコードで行い、課題への適性や委譲の可否は意思決定モデルへ任せる案がある。
候補モデルの情報をどこから取得するかは別途整理する。

判断ごとに親の全コンテキストを再送すると、入力処理と待ち時間が増える。
課題・候補一覧・必要な実行状況など、判断に必要な情報で成立する箇所から試し、
親が判断する場合との費用・時間・選択の妥当性を比較する。
特に検索結果の選別は、親へ渡す情報量の削減効果を測りやすい候補である。

コンパクションの変更は、現在のキャッシュ効果を踏まえて再検討する。
このメモで実装着手を決めたものではない。

## Henjiの実装を参照する

`/home/agent/projects/henji` には、独立した `henji decision` コマンドとして
OpenRouterとOpenAIのDecisions API対応が実装済み。
判断対象をstdin、質問をJSONファイル、provider・modelを引数で指定し、APIの応答JSONを返す。
同じ対象への複数質問を一要求にまとめ、会話DB・履歴を作らずに呼び出す構成である。

## APIの違いと接続案

OpenRouterは `state` と名前付きの質問オブジェクト、OpenAIは `input` と質問配列を使う。
Henjiではそれぞれのネイティブ形式を保持し、OpenRouterは専用HTTP処理、
OpenAIはSDKのDecisions機能で送信している。

hjhではJevだけに固定せず、JSから意思決定を呼び出せる接続を設ける案を検討する。
共通化する操作・結果と、各API固有の質問形式をどこまで残すかは未決。
認証はhjhの既存のcredential管理との関係を整理する。

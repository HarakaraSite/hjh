## 依頼文

hjhの「ツール利用インストラクションの外部化」と「詳しい使い方を検索・取得する辞書ツール」を
一つの改善として調査し、複数スライスの実装計画を作成してください。
ツール間の選び方と、個別機能の詳細を分け、必要な情報をモデルへ効率よく与えることが目的です。

### 背景と利用者の意図

- `600ce255`では、親が並行作業を意図しながら同期型`run_agent`を選ぶ場面があった。
- `64bbc534`のsolは専用toolを使って作業できていた一方、一括編集に`command`経由のPythonを
  選び、当初`run_js`を使っていなかった。Pythonを選んだ理由は履歴からは断定できない。
- その後は`spawn_agent → agent_status → steer_agent`を活用し、`66c5cd0a`では
  `run_js`で変更前ソースの取得・一時ファイル保存・Go overlay生成も行っていた。
  機能が使えない問題ではなく、適する場面で選びやすくする改善を求めている。
- 利用者は`run_js`を活用してほしいが、単独操作まで必ずJavaScriptへ包むことや、
  Python等の利用禁止は求めていない。
- ツールの詳細説明を全て常駐させるとコンテキストが増えるため、詳しい手順・実例は
  必要時に辞書から取得できるようにしたい。

### 必要な動作

**常駐する情報**は、短い共通利用方針と、各toolの名前・用途・引数schema、
正しく呼ぶために必要な最小限の契約とします。
詳しい手順、長い使用例、組合せの説明は辞書へ分ける方向で検討してください。
必須引数や重要な戻り値の意味を、辞書を読まなければ分からない形にしないでください。

共通のツール利用インストラクションには、少なくとも次の意図を含めてください。
文言は読みやすく短く整理して構いません。

- 単独の読取り・編集には専用toolを使う。
- 複数操作の合成、独立した操作の並列実行、結果の集約・加工には`run_js`を優先する。
  単純な文字列・JSON加工だけのためにPython等を起動する場合も、まず`run_js`を検討する。
  外部プログラムやライブラリが必要な処理では適する方法を選ぶ。
- 大きなtool結果は、判断に必要な範囲を取得し、必要に応じて`run_js`で絞り込んで返す。
  正確な判断に必要な原文・識別子・根拠は維持する。
- 子を動かしながら親も作業する場合は`spawn_agent`で開始し、
  親は独立した作業を進め、結果が必要になった時点で`collect_agent`する。
  親に独立した作業がなければ同期実行や開始直後のcollectでもよい。
- 必要に応じてstatusで中間報告を読み、追加指示をsteerで返す。
  pollingや追加指示を機械的に義務化しない。
- 通常の複数tool callは現行loopでは順次実行される。
  同じ応答に複数並べるだけで並列になるとは考えない。
- ツールの選択、引数、組合せ、実行順序に迷ったら、推測で進めず辞書ツールで確認する。

### 調査と設計で決めること

1. **指示の所有と読込み**
   現行のbase instruction、role instruction、`promptGuidelines`、AGENTS.md、skills、
   実行情報の組立てを確認してください。共通利用方針を別の外部ファイルとして編集できる案を
   検討し、個別toolの契約・role固有の指示との責務分担と、移動する既存文言を整理してください。
   `~/.config/hjh/`とworkspaceの`.hjh/`の現行配置・XDG解決を尊重し、具体的な配置、
   未配置時の扱い、上書きか追記か、親ターン・子開始・再開時の読込み時点を提案してください。
   特定ファイル名や優先順位はまだ確定していません。

2. **辞書の内容と取得方法**
   tool名による取得と、目的・キーワードからの検索を成立させる最小のtool APIを提案してください。
   一つのtoolにまとめるか分けるか、結果の形式、該当なしの場合の扱いも決めてください。
   初期の内容は`run_js`と子agent操作を中心とし、専用toolとの使い分け、加工・並列実行、
   spawn/status/steer/collectの実例を含め、今後のtoolも同じ仕組みに載せられる構成にしてください。
   初期版にベクター検索は必須ではありません。名前・キーワード検索で必要な利用例が見つかるかを
   確認して方式を選んでください。検索基盤を先に大きく作らないでください。

3. **既存のtool選択と実行時captureへの接続**
   親・子、定義済みrole、子の明示tools指定で使う経路を確認してください。
   辞書が説明する能力と実際に選択されたtool、capture済み定義と説明の版をどう整合させるか、
   既存の所有者と状態を活用して決めてください。重複したcatalogや別の実行基盤を増やさないでください。

4. **コンテキストと保存量**
   詳細説明を常駐指示から外した量と、辞書取得の追加往復・履歴への追加量を比較してください。
   同じ説明の繰返し取得や、ターンをまたぐ履歴選択・コンパクションとの関係を確認し、
   必要性のないcacheや専用DBを最初から足さないでください。
   辞書本文や実装ソースを各実行へ常時archiveする方式へ戻さないでください。

### 計画書と確認方法

`docs/plans/`へ計画書を作成し、利用者が必要とする動作、現行の入口からモデル入力までの経路、
採用案と理由、外部ファイル配置とAPI、変更・廃止する処理、未確認事項を記載してください。
外部の共通利用方針、辞書の検索・取得、常駐説明の整理を段階的に確認できるスライスに分けてください。

各スライスの実装・focused test・reviewと、最後の総合確認を計画してください。
確認対象は、実際のモデル入力に短い方針が入ること、tool名・目的から必要な実例を取得できること、
親子で現行のtool選択が維持されること、初期の実例が現行APIで動くことなど、具体的なproduct動作に
対応させてください。常駐入力の削減は計測可能な形にしてください。
実モデルによるツール選択の改善は未確認として扱い、必要なら小さな比較課題を提案してください。
offline testの成功だけでモデルの使い方が改善したとは結論しないでください。

### 今回の範囲と報告

調査・設計・計画書作成まで。実装は利用者の確認後です。
動的なtool schemaの公開・非公開、DB非保存mode、usage保存の削減、コンパクション改修、
provider timeoutやリトライ回数の変更は対象外です。
実プロバイダ呼出し、実行中runの操作、常用設定の書換え、DB変更、Core再起動、
コミット・プッシュ・配置は行わないでください。

最後に、推奨する構成、常駐と辞書に置く内容の例、スライス、
利用者の判断が必要な点だけを簡潔に報告してください。
局所的な技術判断は自分で行い、不必要な確認事項を増やさないでください。

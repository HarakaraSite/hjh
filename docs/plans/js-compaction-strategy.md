## 目的と合意した製品動作

コンパクション後に十分な空きを作り、短い間隔での再コンパクションと入力prefixの変更を減らす。
人間が圧縮前の依頼・指針・確認結果を使って作業を継続できることを成功条件とする。

- 通常の発火は現行の有効入力予算90%を維持する。
- 圧縮後は、不変指示・ツール定義・recall prefix・要約・参照・保持原文を含む最終入力を、
  有効入力予算の3分の1以下にする。ウィンドウ全体の3分の1以下という当初の条件も満たす。
- 要約は原則一回とし、目標超過時だけ追加一回で終了する。
  追加後も目標を超える場合は、継続可能な候補のうち小さい方を採用し、目標未達を記録する。
- 不変指示の巨大化に対する特別な処理は設計しない。
- `不変指示 > A > B > C > D > E`の例では、A・Bは削除を第一選択とし、
  Eから参照すべき指針・結果だけを要約へ残す。C・DはE以降の継続に必要な内容へ要約する。
  Eの継続に必要な直近原文を保持する。
- Eだけで目標量を超えるときは、既存のターン内コンパクションに従う。
  古い完了済み交換を要約し、現在の依頼・適用済み追加指示・直近の継続部分を保持する。
  ツール呼出しと結果は完全な交換単位で扱う。
- 復元後の最初の要求では、先に入力予算に収まるまで古い完了ターンを入力候補から外し、
  残った候補へ上記の圧縮処理を適用する。
- 削除はモデル入力からの除外であり、保存済み原文を削除・書換えしない。

OpenCode Go / DeepSeek V4.1 Flashの実利用と、検証用閾値の任意値への上下調整は利用者が許可済み。
小さい入力で確認できる任意値も使う。計画レビュー後、利用者が本計画の実装・テスト・コードレビューと
その後の実測を明示的に指示した。
要約は現行どおり親のprovider・model・effortを継承する。
利用者の指定により、要約用provider/modelの任意指定は別タスクとし、本計画の対象外とする。

## 現行の製品経路と変更理由

```text
CLI / TUI → Core / app.Service → app.execute → agent.Run
  → projectRequest → 外部compaction.js
    → context.get / history / measure / select
    → model.generate（親と同じprovider/model/effort、一回の問い合わせ）
    → context.replace / memory.set
  → providerへ圧縮後の通常要求 → 回答・会話採用 → Sessionメモリ公開
```

| 責務 | 現行sourceと状態 |
| --- | --- |
| 圧縮方針・要約instruction・coverage・保持境界 | `examples/hooks/compaction.js`。常用workspaceにも`.hjh/extensions/compaction.js`があり有効化済み |
| 原文の供給 | `internal/app/request_context.go`の現在ターンと、`context_budget.go`のcanonical履歴reader |
| 入力予算・計量・交換選択 | `internal/contextbudget/`と`internal/app/request_context_selection.go` |
| 要約の一回model呼出し | `internal/app/request_model.go`。親と同じ解決済み接続を使う |
| Session内の要約状態 | `internal/app/context_memory.go`。実行内で更新し、正常canonical採用後に公開。Core再起動後は空 |
| 呼出し時刻・usageの観測 | `internal/jsruntime/request_context.go`、`observations.go`、`worker.go`。Host callと外側hookの開始・終了を記録 |

現行は、履歴を最初の予算超過ターンまで追加し、その超過ターンも要約対象に含める。
発火後は原文目標60%で選択してから要約を追加し、最終入力は通常予算で選択する。
要約は配列へ追加し、既存要約自体は整理しない。このため最終入力全体の圧縮目標がなく、
復元時にも予算から外すべき古いターンを要約し得る。
また要約モデルへ渡す継続情報は主に最初のuser taskであり、Eの直近状態が十分に含まれない。

## 設計と処理順

### 発火量と最終目標量

`L`を既存resolverによる有効入力予算とする。
通常発火量は`0.9 × L`、最終目標は`floor(L / 3)`とする。
例えば有効入力予算20,000では18,000で発火し、最終入力6,666以下を目標にする。
ウィンドウが大きくても設定上の入力予算が小さい場合に、目標が発火量以上になる式は使わない。
`L`が不明なら現行の800,000入力予算を使い、既知のモデル予算を800,000で制限しない。

`rawTargetRatio`を最終入力全体の目標へ置き換える。要約を加えた後に既存`measure`で再計量し、
目標達成を判定する。要約本文や参照も計量に含める。
モデルへの文字数指定だけを目標達成の証拠にしない。追加一回後の目標未達の扱いは後述する。

検証設定は発火量と目標量をそれぞれ任意の小さいtoken値でも指定できるようにする。
通常経路で再発火間隔を確認するときは、発火量が目標量より大きい関係を保つ。
検証用値は独立workspaceの設定へ置き、使用した有効値・比率・入力規模を証跡へ残す。

### 削除・要約・保持

1. 現在ターン、保持対象のcanonical履歴、既存要約を集める。
   前回の処理済み境界より古い原文を復活させない。
2. 非発火時は既存要約の本文・順序と保持境界を維持し、新しい会話だけを追加する。
   毎要求での要約し直しや要約の書換えを避ける。
3. 発火時は、遠い過去・近い過去・Eの原文を区別する。
   初期案は直近の完了2ターンをC・D相当、それ以前をA・B相当とする編集可能なJS方針。
   これは例を固定5ターンへ限定する仕様ではない。巨大なEはターン内交換単位で扱う。
4. Eの保持部分を選び、不変指示・ツール定義・prefix・原文を含む保持側の量を計量する。
   最終目標から保持側の量を差し引き、参照も含む要約に使える量を決める。
   要約モデルへ、Eの依頼・適用済み追加指示・直近状態、既存要約、今回扱う過去範囲と
   この要約量の目安を渡す。
   遠い過去は網羅的に保存せず、Eに必要な指針・結果だけを抽出するよう指示する。
   近い過去は継続目的・採用判断・確認結果・未完了作業をまとめる。
5. 既存要約も今回の必要性に応じて整理・統合する。
   通常は一回の要約要求で新しい継続要約を作り、追加蓄積する経路を置き換える。
   原文参照はJSが実在sourceから組み立て、本文と対応する参照・保持境界を同じstateで更新する。
6. 新要約と保持原文を組み立てて最終計量する。目標以下ならその候補を採用する。
   目標を超え、保持側にさらに移せる古い完了交換がある場合は、その交換を追加要約対象へ回す。
   移せる交換がない場合は、継続要約を短くまとめ直す。
   どちらも追加のmodel要求は一回だけとし、最初の要約と合わせて一回のコンパクションにつき最大二回で終了する。
   追加要求では、最初の要約と追加対象の原文、Eの判断情報から継続要約全体を作る。
   追加後も参照込みで計量し、最初の候補から減った量と目標達成状況を記録する。
   なお、保持必須部分だけで目標を超える場合は、後述の既存ターン内動作に従い、
   要約を短くしても目標へ届かないことだけを理由に追加要求を繰り返さない。
   追加後も目標を超える場合や縮まらない場合は、必要な依頼・追加指示・直近部分を保持して
   継続できる候補のうち、計量した最終入力が小さい方を採用する。目標未達は未達のまま記録する。
   有効入力予算内なら継続し、その予算自体を超える場合は既存の予算超過処理に従う。
   追加のmodel要求は実測へ全て算入する。
7. 最終要求と、削除済み・要約済みの原文範囲を確定する。要約に残さなかった原文も
   処理済み境界で扱い、次のstep/turnに再投入・再要約しない。
   候補ごとに本文・参照・coverage・保持境界を一組で保持し、採用した候補に対応するstateだけを確定する。
   stateの公開は既存の正常採用境界を使う。

要約入力自体も親モデルの有効入力予算へ収まるよう、instructionやEの判断用情報を含めて計量する。
復元時に予算から外した古いターンは、要約へも投入しない。
通常継続では最初の超過ターンも要約候補へ含める。近い履歴が一度の要約入力へ収まらない場合は、
古い側を先に要約し、残りを第一候補へ原文で保持して、第二要求で統合する。
この分割・統合も最大二回の枠内で行い、未処理の原文を保持境界や最終selectだけで落とさない。

現在のselectorが保持する依頼・追加指示・最新交換だけで目標を超える場合は、既存のターン内動作に従う。
3分の1の達成状況と実際の保持量を記録し、目標超過を理由とする新しい拒否条件は設けない。

### セッション復元

復元処理の対象は、要約stateがない状態で既存canonical履歴を使う最初の要求とする。
Core再起動・別CLI processが該当する。同じCoreへの再接続でstateが残っている場合は通常継続を使う。

最新から完了ターンを追加して計量し、入力予算を超える古いターンは入力候補へ採用せず、そこで探索を止める。
続いて、残った候補が最終目標量を超えていれば削除・要約を行う。
復元初回は、通常の90%発火量まで膨らむのを待たない。
Eだけで大きい場合は同じターン内コンパクションへ進む。
復元後のstep/turnには確定した境界と要約を引き継ぐ。

要約checkpointのDB永続化は今回含めない。
明示from-turn変更時は、既存どおり選択範囲外のstateを再利用しない。

## 実装段階と対象

1. **JS方針の変更**：`examples/hooks/compaction.js`を中心に、最終目標・削除優先・要約統合・
   Eの判断情報・復元時の事前選択を実装する。helperは履歴収集、計量、範囲選択、要約生成、state更新の
   責務で分ける。現行APIで成立する範囲ではGoの汎用APIを増やさない。
2. **実経路のfocused確認**：`internal/app/compaction_test.go`の実QuickJS/Service経路を更新する。
   旧方針の「要約配列を追加し続ける」「遠い過去を全て要約する」期待は新方針へ合わせる。
   決定的なproviderによる確認は選択・計量・境界を対象とし、意味上の要約品質は実モデルで確認する。
3. **独立Core/CLIによる機能確認・時間実測**：再現用scriptを`scripts/verify-compaction-strategy.py`へ置く。
   通常のCore・接続CLI・拡張読込み・canonical採用・履歴読戻しを使う。
   実測用workspace/DB/configと起動Coreを独立させる。
4. **確認と文書更新**：defaultが差分・実操作結果をreviewし、採用済み動作を
   `docs/design/js-compaction.md`と必要な`docs/design/request-context.md`へ反映する。
   `docs/results/js-compaction-strategy.md`と集計JSONへ結果・時間・未確認範囲を記録する。

常用`.hjh/extensions/compaction.js`への反映、常用Core再起動、配布物更新は本計画の検証と分ける。
実装結果を確認するまでは現行の常用設定を切り替えない。

## 動作確認と根拠

| 合意した動作 | 確認する利用経路と結果 |
| --- | --- |
| A・Bは削除優先、必要な指針・結果だけ残す | A・Bに継続に必要な指針と完了済み別件を置き、Eの実作業で指針を使えること、不要原文が最終入力から外れること、明確な別件情報が継続要約にも残らないことを確認 |
| C・DをEの継続用に要約 | C・Dの確認済み値・未完了作業をEで利用し、元fileの再読取りに頼らず結果を完成できることを確認 |
| 最終入力が有効入力予算の3分の1以下 | 入力予算がウィンドウより小さい設定も使い、要約・参照込みの最終量と発火量・目標量を照合。hjh推定値とprovider報告usageは分けて記録 |
| 追加要約は必要時一回で終了 | 最初の要約で目標達成する経路と、追加後も超過・縮小なしの経路をfocused確認。最大二回で終わり、採用候補の本文とstateが対応し、予算内なら継続できることを確認 |
| E単独でもターン内圧縮 | 大きいtool結果を順に取得し、古い完全交換の要約後も直近の結果・追加指示を使って回答できることを確認 |
| 復元は先に予算へ収める | 予算を超えるcanonical履歴を用意して独立Coreを再起動。外した古いターンが要約入力へ入らず、残した履歴から継続できることを確認 |
| 圧縮直後の再発火を減らす | 同じ追加作業を圧縮後も継続し、次回発火までのstep/turnと追加推定tokens、要約呼出し回数を旧方式と比較 |
| 原文と状態の対応を維持 | CLI history/inspectで原文・参照を照合し、同じCoreの次turnで削除済み範囲が復活しないことを確認。既存の失敗・取消時の非公開契約は関連focused testで維持を確認 |

実装中は変更箇所のfocused testと`git diff --check`を使う。

Go変更がある場合だけ変更に応じたformat/staticcheck・既存メモリ境界のfocused raceを行う。
repository全体のgateやpermission/入力matrixは追加しない。

## OpenCode Go / DeepSeek V4.1 Flashでの所要時間実測

### 条件と測定範囲

親・要約とも`opencode-go-chat / deepseek-v4.1-flash`を使い、初期effortは既存実績の`auto`で揃える。
開始時に実際の解決済みprovider/model/effortと有効予算を記録する。
credentialは既存の参照経路を使い、値やAuthorizationをscript出力・証跡へ出さない。

通常のターン間圧縮、Eのターン内圧縮、Core再起動後の復元初回を測る。
同じ代表履歴・設定・継続依頼を旧方式と新方式にそれぞれ与え、圧縮量・継続結果・待ち時間を比較する。
元履歴の準備にかかった生成時間は圧縮時間へ算入しない。

小さい任意の発火値・目標値で動作確認した後、数万token級と10万token級を目安に
入力規模を変えて実測する。実際のprovider報告入力tokensも記録する。
規模ごとに検証用のwindow/入力予算と発火量・目標量の関係を設定し、
圧縮前が発火量を超え、圧縮後の目標が圧縮前より小さくなる条件を作る。
低い発火値だけを使った小入力実測を、通常の大きいコンテキストでの所要時間へ外挿しない。

各代表条件は初回値を含めてまず3回測り、各実測値・中央値・最小〜最大を示す。
これはネットワークと生成の変動を見るための測定反復であり、test件数の目標ではない。
少数測定のp95や一律の「何秒以内」を合格基準にしない。
旧新の実行順を交互にし、時刻・cache報告値を残す。条件差や測定失敗は結果へ明記する。

### 記録する値

| 値 | 測り方・意味 |
| --- | --- |
| 要約呼出し一回の時間 | `context.model.generate`の同一call IDの開始〜完了。provider処理・通信・bridgeの時間を含む |
| 要約呼出しの合計時間 | 一回の圧縮に属する全要約呼出しを合算。目標達成のための追加要約も含む |
| コンパクション全体時間 | 発火した`projectRequest` hookの開始〜完了。履歴読込み、計量、範囲選択、要約、差替え、state設定を含む |
| 要約以外の時間 | hook全体時間から要約呼出し合計を差し引く。既存の直列呼出し経路を前提とする |
| 利用者の待ち時間 | 接続CLIの依頼送信〜最終回答。通常の親model生成を含み、コンパクション時間と分ける |
| 圧縮の効果 | 圧縮前後の推定tokens・wire bytes・比率、削除/要約/保持範囲、要約文字数、model要求数 |
| 利用量と再発火間隔 | providerの入力/出力/reasoning/cacheの報告値（存在する項目）、次回発火までの追加量・step/turn |

Host callとhookの親子ID・既存の開始/終了時刻で対応を取る。CLI全体は外側scriptのmonotonic clockで測る。
圧縮前量や削除・要約範囲は既存観測のbyte数だけでは再構成できないため、検証用hook wrapperで
`measure/select/memory.set`等を透過的に呼び、返された計量値と適用stateから必要な数値・範囲だけを
独立workspaceのJSONへ出す。実行ID・model step・要求内の順序を付けて時刻の観測と対応付ける。
本文は通常の最終snapshotで確認し、検証JSONには要約文字数・目標達成状況・採用候補と追加回数を残す。
専用の計測API・DB表・要約送受信全文archiveは追加しない。
cache値が返らない場合は未報告とし、prefixの安定や呼出し間隔だけからcache hitを断定しない。

### 成果物と完了条件

結果文書に、各条件の設定、入力規模、実作業の成否、旧新の圧縮率・秒数・呼出し回数を表で示す。
集計JSONと再現script、独立DB/CLI出力等の証跡pathを対応付ける。
従来の実測はturn全体約8〜10秒であり、要約単体の時間ではない。今回の比較基準は同条件で測り直す。

# コンパクション有無の課題実行比較

2026-10-16、OpenCode Go / DeepSeek V4.1 Flash / effort=autoで実施した。
同じリリース計画の課題を2組比較した範囲では、圧縮の有無で成果物と追加修正の内容は一致した。
ただし、圧縮側では採用した数値を保持していても、その採用理由が後から答えられなくなる場合があった。
作業に関係しない完了済みの別件の詳細は、圧縮側では2回とも回答できなかった。

## 比較方法

独立したCore・workspace・SQLite DBを4環境作り、各組で同じ過去4ターンとCSVを与えた。
履歴Aは採用済みの仕様と未採用案、Bは完了済みの図書館搬入、Cは候補検証と例外、Dは最新の訂正である。
過去の検査ログを含むA〜Dは合成データで、loopback providerと通常のCore/CLI経路から準備した。
事前履歴をDBへ直接注入していない。準備部分は実モデルによる作業実績ではない。

その後の以下の3ターンと圧縮要約は実モデルで実行した。1組目は圧縮なし→あり、2組目はあり→なしの順。
各組の準備履歴はcanonical messagesの内容が完全一致し、組をまたいでも同一だった。

1. 会話で合意した仕様・検証結果・最終訂正を使い、CSVから`rollout-plan.json`を作成する。
2. tokyoのpercentだけ25へ変更し、他の全項目を維持して保存する。
3. 125msを採用した理由と試験ID、別件の搬入予約番号・搬入口・担当者を会話だけから答える。
   不明な詳細は不明と答えるよう、両条件に同じ指示を与える。

両条件とも入力予算は60,000推定tokens。圧縮側だけ発火10,000、圧縮後目標4,500に設定し、
要約長は製品既定の約1,200文字、直近完了ターン数は2を使用した。要約モデルは親を継承する。
準備中は両条件とも十分大きな発火値・目標値で同じhookを使い、同一Core内の継続として比較した。
圧縮なし側は観測用hookから通常の選択を観察し、置換・要約は行っていない。
圧縮なし側の全16モデルステップで履歴は`full`、省略なし、予算内だった。

これはターン間の圧縮とその後の継続を観測したもので、復元やターン内圧縮の比較ではない。
実行は合計12課題ターン、通常モデルステップ29、要約生成2回。

## 観測した動作

| 観測対象 | 圧縮なし（2回） | 圧縮あり（2回） |
| --- | --- | --- |
| 合意済みschema・channel・通知先・region順序 | 両方正しい | 両方正しい |
| 125ms基準、CSV上passedでもrel-736を除外 | 両方正しい | 両方正しい |
| 最終訂正tokyo=5、osaka=10を反映 | 両方正しい | 両方正しい |
| tokyoだけ25へ変更し、他の項目を維持 | 両方正しい | 両方正しい |
| 根拠試験ID PERF-Q17-125の再回答 | 両方回答 | 両方回答 |
| 130ms案を退けた理由の再回答 | 両方回答 | 1回回答、1回不明 |
| 別件の予約番号・搬入口・担当者の再回答 | 両方回答 | 両方不明 |

成果物は報告文だけでなく、workspaceに保存されたJSONの全項目を期待内容と比較した。
どの実行もosaka=rel-734/rollback rel-730、tokyo=rel-842/rollback rel-840を選んだ。
初期percentは10/5、変更後は10/25で、不要な項目の追加もなかった。
1組目はファイルのバイト列も同一。2組目は空白・整形が異なるがJSONの内容は同一だった。

最も明確な差は、1組目の理由の欠落だった。原文には「ピーク時間帯の再試験で130ms案に
タイムアウトが出た」とある。圧縮要約は次のように、基準と試験IDを残して理由を省いた。

> 選定ルール: candidates.csvでstatus=passedかつp95_ms<=125の候補のみ対象。
> …125ms根拠の試験IDはPERF-Q17-125。

後から理由を尋ねると、圧縮側は「130ms案ではなく125msを採用した理由: …不明です」と回答した。
圧縮なし側はピーク時間帯の再試験でのタイムアウトと試験IDを回答した。
2組目の要約には理由も残り、その後の質問にも正しく回答した。同じ入力でも要約の細部に揺れがある。

図書館搬入は現在のリリース作業と無関係なので、圧縮要約には両回とも詳細が残らなかった。
後から別件へ話題を戻すと、圧縮なし側は`LIB-6092`・`西口3`・`森さん`を回答し、圧縮側は全項目を
不明と回答した。これは古い無関係な完了事項を削除する採用方針に沿った結果である。
原文はcanonical履歴に保存されているが、この比較でモデルに与えた道具はread_file/write_fileで、
canonical履歴を再取得する道具は与えていない。
圧縮側の回答には「会話に記載がない」という表現もあったが、正確には投影されたコンテキストで
確認できなくなったものであり、保存済み履歴から消えたわけではない。

操作手順にも差はあった。圧縮なし側は両回とも作成・変更後にファイルを再読し、圧縮側には保存後の
再読がなかった。圧縮側の1回目の変更では保存前に再読した。いずれも実ファイルは正しく保存された。
1組目では両条件ともread_fileでディレクトリを読もうとするエラーが1回ずつあったが、作業は完了した。
これらの手順差を、2組の結果だけから圧縮の一般的な効果とは判断しない。
採用済み方針を質問し直す動作や、完了した計画作成をやり直す動作は観測しなかった。

## 解釈と記録

今回の課題では、現在の作業に必要な採用値・例外・最終訂正は維持され、ファイル作成と追加修正を
完了できた。一方、採用値を支える理由や、後で別の話題へ戻ったときの詳細は失われうる。
特に理由は、同じ入力でも残る回と落ちる回があった。理由まで確実に残したい場合には、
「継続に必要な結果」の扱いを理由まで含めるかが、追加で判断する点になる。
この観測を受けた要約指示・製品実装の変更は行っていない。

一種類の合成履歴に対する2組の定性的観測であり、成功率や一般的な品質差を推定するものではない。
大きなログの各行も合成データで、実利用の長期的な履歴や複雑なコード修正を再現した評価ではない。
比較設定は独立したworkspaceだけに配置した。

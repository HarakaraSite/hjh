# コンパクション方針の変更と所要時間

2026-10-16。[計画](../plans/js-compaction-strategy.md)に基づいてJS拡張とテストを実装し、
コードレビュー・関連パッケージの確認と、実providerでの反復測定を完了した。
現行契約は[JSコンパクション](../design/js-compaction.md)、再現手順は
[検証スクリプト](../../scripts/verify-compaction-strategy.py)を参照する。

## 実装した動作

- 通常発火は有効入力予算Lの90%、圧縮後の最終入力目標はLの3分の1。
  要約・参照・不変指示・ツール定義・保持原文を含めて計量する。
- 古い完了turnは削除優先で、現在の依頼Eに必要な指針・結果だけを継続要約へ残す。
  直近の完了2turnは継続用に要約し、既存の要約も一つに統合する。
- Eの古い完了交換は対応するtool call/result単位で扱い、依頼・追加指示・直近部分を保持する。
  要約モデルにもEの依頼・追加指示・直近状態を渡す。
- 要約は原則1回、必要時だけ追加1回。縮まらない追加応答を受けても繰り返さず、
  継続できる小さい候補と、その本文に対応するcoverage・参照・保持境界を採用する。
  目標未達でもL以内なら継続し、L超過は既存の予算判定へ渡す。
- 復元初回だけ、先に古い完了turnを入力予算まで外す。通常継続では最初の超過turnも
  要約候補へ入れる。要約入力に近い履歴が一度で入らない場合は、最大2回の中で分割・統合する。
- 最終候補はexact replaceで適用し、要約していない必要原文を後段のselectで黙って落とさない。
  原文DB・既存の正常採用後のSession state公開・親モデル継承は維持する。

## 実providerの測定条件

親・要約とも`opencode-go-chat / deepseek-v4.1-flash / auto`。
独立workspace/Core/DBで、準備はlocal providerを通した通常のcanonical採用経路を使い、
計測対象の依頼から親・要約を実providerへ切り替える。準備時間は測定値へ含めない。
復元条件では準備後に独立Coreだけを再起動する。

ターン間・ターン内・復元初回の3条件を、名目3万・12万のhjh推定tokens規模で旧新各3回、順序を交互に測る。
名目規模は入力データの設定値であり、実際の候補の推定量とprovider報告入力tokensは別に記録する。
通常発火・目標の比率を維持し、既知の入力予算を検証用に設定した。
この比較では旧新とも`summaryCharacters=700`へ揃え、製品の通常値1,200文字については
名目3万のターン間圧縮で旧新各3回を別に確認する。文字数はsoft targetであり、本文の切詰めは行わない。

要約時間は保存された`context.model.generate`のcall IDで開始・終了を対応付ける。
コンパクション全体は外側`projectRequest` hookの開始〜終了で、検証wrapperの記録処理も含む。
`compact()`単体の区間も別に記録する（Date.now、ミリ秒のwall clock）。CLI時間は外側monotonic clock。
追加要約があれば、その時間と要求数も合計へ含める。

初回の実モデル試運転では必要4値の継続回答は成功したが、要約に不要な別件IDを
「除外する」という注意書きとして残した。除外対象の名前・列挙・説明も書かないよう要約instructionを明確化し、
focused test後に測定をやり直した。初回試運転は反復測定の集計へ含めない。
本文のlocal加工・切捨てで結果を作る処理は追加していない。

測定途中、検証側がEの「博物館情報は不要」という現行指示まで不要履歴と判定したため、
別件固有ID・予約事実の混入だけを検出するよう修正した。Eの指示を保持する正常な要約は許容する。
完了済みの測定値は保持し、失敗した試行を別directoryへ残して未完了条件を再開した。
再開は記録済みのcase keyを使い、時刻・usageの補間や書換えはしない。

各条件で旧新それぞれ3回実行した。下表はコンパクション全体の中央値と最小〜最大、

| 3万 | ターン内 | 7.79（6.40〜9.39） | 20.71（12.03〜30.75） | 33,700 → 11,460 |
| 3万 | 復元初回 | 13.81（10.35〜19.53） | 19.07（17.36〜28.72） | 31,890 → 1,891 |
| 12万 | ターン間 | 22.82（8.02〜25.38） | 17.77（5.03〜20.67） | 122,702 → 1,794 |
| 12万 | ターン内 | 14.38（10.41〜25.99） | 17.72（12.53〜23.78） | 124,640 → 38,500 |
| 12万 | 復元初回 | 24.54（21.14〜27.93） | 13.21（11.86〜59.52） | 122,702 → 1,867 |

新方式のコンパクション全体中央値は条件別で約13〜23秒、観測範囲は約5〜60秒だった。
旧新とも1回の時間は変動し、新方式の方が長い条件もある。cache・reasoningを含むprovider応答と通信を
分離した測定ではないため、入力規模だけから秒数を予測しない。

全条件で4値（AX-314、BY-271、CZ-161、amber）を引き継いで回答し、保存原文と参照を照合できた。
新方式は18回中17回で最終目標を達成した。3万のターン内1回は、参照だけの空noteを置いても
保持側が11,713で目標11,471を超えていた。2回の要約後は11,981、入力予算34,414以内で継続した。
これは合意したEの保持優先・目標未達記録の経路である。その他の新方式は要約1回で完了した。

大きい条件の要約API入力はprovider報告で、新81,480〜82,101、旧66,269〜100,259 tokens。
通常要求の入力推定と要約APIの入力usageは異なる計量であり、両者を置き換えない。
要約API以外の時間、CLI全体、reasoning/cache報告値、各回の値は
[集計JSON](js-compaction-strategy-data.json)と元の`reports.json`へ残した。
要約APIのcached_tokensは実際に返された値を記録したが、長期の通常会話でのcache改善率は測定していない。

証跡：`/tmp/hjh-compaction-strategy-wvuVHX3a/live/compaction-g8u9exhb/reports.json`。

## 通常の1,200文字目安での追加確認

名目3万のターン間圧縮を、`summaryCharacters=1200`で旧新各3回測定した。
発火量・入力予算・依頼・元履歴・親provider/model/effortは比較測定と同じである。

| 方式 | 要約API秒：中央値（範囲） | 圧縮全体秒：中央値（範囲） | CLI最終回答まで秒：中央値 |
| --- | ---: | ---: | ---: |
| 旧 | 23.58（21.88〜41.62） | 23.61（21.91〜41.66） | 28.30 |
| 新 | 16.43（5.89〜21.50） | 16.46（5.92〜21.53） | 19.77 |

新方式は3回とも4値を引き継ぎ、目標11,471以下の1,643・1,643・2,024推定tokensへ圧縮できた。
本測定では要約は各1回で完了し、原文・参照の照合も成功した。
700文字条件との時間差にはモデル応答の変動やcache状態も含まれ、文字数設定の効果だけを比較する実験ではない。

証跡：`/tmp/hjh-compaction-strategy-wvuVHX3a/live-default-length/compaction-9e1tiu4u/reports.json`。
各回の時刻・usageは元証跡、条件別の集計は[集計JSON](js-compaction-strategy-data.json)の
`defaultLengthMeasurement`へ記録した。再集計scriptは
`/tmp/hjh-compaction-strategy-wvuVHX3a/summarize-results.py`。

今回の時間は要約API往復を含む観測値であり、通常設定で常に16秒台になる保証値ではない。
比較測定でのAPI以外の処理は約0.024〜0.099秒だった。

## 適用範囲

常用`.hjh/extensions/compaction.js`は旧方式のままで、保持した旧sourceとSHA-256が一致する。
常用Core/DB、配布物、credential file、保存原文の削除・移行は変更していない。
要約用provider/modelの任意指定は別タスク。永続checkpoint、長期間のcache改善率、
未測定規模・他providerの所要時間は今回の結果に含めない。
